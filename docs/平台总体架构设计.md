## 1. 总目标

AI4SEC 平台的目标不是重写一个日报脚本，而是建设一个统一的 AI 安全洞察平台：

```text
外部数据源
  → 原始制品
  → 结构化条目
  → 领域对象
  → 模型审阅 / 规则评分 / 复现验证 / 质量审计
  → 前端工作台
  → 人工队列和后续行动
```

平台要融合现有几类流程：

| 旧流程 | 当前位置 | 新平台归属 |
|---|---|---|
| AI-for-Sec 日报 | `/home/liuqi777/ai-for-sec-report`、`insight-platform` | 资讯洞察 + 能力洞察上游 |
| 华为 repo / CVE / 固件情报 | `repo-info/huawei` | 威胁洞察 |
| 漏洞素材采集 | `vul-info/project_demo_0626` | 漏洞洞察 |
| 代码复现系统 | 生产大屏 v1 / repro runner | 能力洞察、漏洞洞察、威胁洞察共用执行能力 |

## 2. 业务域划分

平台按四个业务域和一个统一运营后台组织。

```text
AI4SEC 平台
├── 资讯洞察
├── 能力洞察
├── 威胁洞察
├── 漏洞洞察
└── 统一运营后台
```

| 业务域 | 核心问题 | 主要对象 |
|---|---|---|
| 资讯洞察 | 今天有什么 AI 安全、代码安全、Agent 安全相关动态值得看 | 资讯、论文、项目、日报条目、摘要、技术点 |
| 能力洞察 | 哪些前沿论文、工具、项目可以转化为实际能力 | 能力候选、能力卡、复现任务、复现结果、能力转化队列 |
| 威胁洞察 | 哪些开源目标、仓库、组件、固件、镜像值得挖 | 目标仓库、CVE、固件、镜像、攻击面、风险评分、跟踪队列 |
| 漏洞洞察 | 哪些外部漏洞素材、PoC、根因模式可以迁移到我们的目标上 | 漏洞素材、PoC、根因模式、触发条件、关键函数、迁移候选 |
| 统一运营后台 | 数据源、采集任务、规则、质量、人工队列是否健康 | 采集任务、数据源、规则配置、质量审计、人工队列 |

## 3. 技术栈选择

### 3.1 后端

```text
Python 3.11+
FastAPI
Pydantic v2
SQLAlchemy 2.x 或 SQLModel
Alembic
```

选择原因：

- 现有采集、LLM、pipeline 代码都在 Python 生态。
- FastAPI 适合前后端分离和 OpenAPI。
- Pydantic 适合维护结构化 schema。
- SQLAlchemy / SQLModel 适合从 SQLite 平滑迁移到 PostgreSQL。

### 3.2 数据库

```text
开发 / shadow：SQLite
正式运行：PostgreSQL
```

第一阶段先用 SQLite，把表结构和 API 跑通。不要一开始被数据库部署拖慢。

### 3.3 前端

当前：

```text
demo/index-v9.html 作为产品信息架构原型
```

正式工程建议：

```text
React + Vite + TypeScript
```

前端不应该直接读取旧目录和 JSON 文件，而应该请求平台 API。

### 3.4 模型层

继续使用：

```text
OpenAI-compatible API
LLMProvider
LLMRouter
model profile
```

业务代码不能写死具体模型。模型选择通过配置完成。

### 3.5 任务运行

第一阶段不要上复杂队列。先用：

```text
PipelineRunner + CLI + FastAPI 触发
```

后续再逐步接入后台任务、任务队列、定时调度和分布式 worker。

## 6. app 目录设计

`app/` 是 FastAPI 应用层，只处理 HTTP 请求、参数解析、依赖注入和返回响应，不写业务细节。

```text
src/ai4sec_platform/app/
├── __init__.py
├── main.py
├── dependencies.py
├── error_handlers.py
└── api/
    ├── __init__.py
    ├── router.py
    ├── news.py
    ├── capabilities.py
    ├── threats.py
    ├── vulnerabilities.py
    ├── operations.py
    ├── runs.py
    ├── artifacts.py
    └── health.py
```

| 文件 | 职责 |
|---|---|
| `main.py` | 创建 FastAPI app，挂载总路由、异常处理、启动检查 |
| `dependencies.py` | 提供 DB session、settings、当前用户、分页参数等依赖 |
| `error_handlers.py` | 统一处理业务异常、验证错误、系统错误 |
| `api/router.py` | 汇总所有业务路由 |
| `api/news.py` | 资讯洞察 API，例如今日资讯、资讯列表、详情、反馈 |
| `api/capabilities.py` | 能力洞察 API，例如能力候选、复现任务、能力卡 |
| `api/threats.py` | 威胁洞察 API，例如目标库、目标详情、跟踪队列 |
| `api/vulnerabilities.py` | 漏洞洞察 API，例如素材库、知识提取、迁移队列 |
| `api/operations.py` | 统一运营 API，例如采集任务、数据源、规则、人工队列 |
| `api/runs.py` | PipelineRun / TaskRun 查询、触发、重跑 |
| `api/artifacts.py` | 制品列表、制品详情、下载或预览 |
| `api/health.py` | 健康检查 |

API 层只能调用：

```text
domains/*/service.py
ops/*.py
pipelines/runner.py
db/repositories/*.py
```

API 层不应该直接调用具体 connector、具体 Agent、旧系统脚本或直接读取旧 raw 文件。

### 12.4 PipelineRunner 是什么

位置：

```text

```

作用：

```text
真正执行 pipeline。
负责创建 PipelineRun、逐步执行 step、创建 TaskRun、写 manifest、处理错误。
```

核心调用逻辑：

```text
PipelineRunner.run(pipeline_name, params)
  → 从 PipelineRegistry 取 PipelineDefinition
  → 创建 pipeline_runs 记录
  → 创建 PipelineContext
  → for step in pipeline.steps:
        创建 task_runs 记录
        执行 step.run(context)
        保存输出 artifact
        更新 context.outputs
        更新 task_runs 状态
  → 生成 manifest
  → 更新 pipeline_runs 状态
  → 返回 run summary
```

### 12.5 PipelineRun 和 TaskRun 是什么

它们不是 Python 目录，而是数据库运行记录，同时有 schema 和 repository。

位置：

```text
db/models/runs.py
db/repositories/runs.py
schemas/runs.py
pipelines/runner.py
```

关系：

```text
一个 PipelineRun
  包含多个 TaskRun

一个 TaskRun
  对应一个 PipelineStep 的一次执行
```

## 13. 标准 Step 文件职责

| 文件 | 类名 | 调用对象 | 输出 |
|---|---|---|---|
| `collect.py` | `CollectStep` | `SourceRegistry`、`SourceConnector`、`ArtifactStore` | raw artifact |
| `import_existing.py` | `ImportExistingStep` | 旧系统 adapter、`ArtifactStore` | imported artifact |
| `normalize.py` | `NormalizeStep` | `domains/*/normalizers.py` | `normalized_items` |
| `dedupe.py` | `DeduplicateStep` | `domains/*/dedupe.py` | deduped items、duplicate groups |
| `fetch_content.py` | `FetchContentStep` | connector 或内容抓取服务 | content artifact |
| `extract_evidence.py` | `ExtractEvidenceStep` | domain 规则或 Agent | `evidence` |
| `llm_review.py` | `LLMReviewStep` | `agents/*`、`models/router.py` | review artifact、model_calls |
| `select.py` | `SelectStep` | `domains/*/selectors.py` | selected items |
| `summarize.py` | `SummarizeStep` | `agents/report_summary.py` | summaries |
| `build_domain_item.py` | `BuildDomainItemStep` | `domains/*/builders.py` | `domain_items` |
| `render.py` | `RenderStep` | domain renderer | final report artifact |
| `audit.py` | `AuditStep` | `domains/*/audits.py`、`ops/quality.py` | quality audit |

标准 step 调用链：

```text
PipelineRunner
  → Step.run(context)
  → Step 读取 context.inputs / context.outputs
  → Step 调用公共模块或 domain 模块
  → StepResult 返回 metrics、artifact refs、db records
  → Runner 更新 TaskRun
```

## 24. 四个业务域如何复用采集功能

四个业务域都需要外部数据源，但不应该各自实现采集框架。


公共框架负责：

```text
任务运行
错误记录
重试策略
原始制品保存
checksum
manifest
数据源状态
质量审计入口
```

示例：

```text
资讯洞察 pipeline
  connectors: arxiv, github, rss, x_feed, asis, awesome

  builder: domains/news/builders.py

威胁洞察 pipeline
```

## 35. 核心数据处理落地结构

当前核心数据处理不新增顶层 `processing/` 目录，而是复用既有公共模块：

```text
schemas/classification.py
schemas/scoring.py
pipelines/steps/classify.py
pipelines/steps/score.py
```

### 35.1 公共能力

| 能力 | 文件 | 说明 |
|---|---|---|
| 分类结果 | `schemas/classification.py` | 输出 category、subcategory、tags、confidence、reasons、signals |
| 评分结果 | `schemas/scoring.py` | 输出 score、priority、grade、breakdown、reasons、signals |
| 分类编排 | `pipelines/steps/classify.py` | 接受领域 classifier，写回 `classification` |
| 评分编排 | `pipelines/steps/score.py` | 接受领域 scorer，写回 `score` 和 `scoring` |

### 35.2 领域策略

| 领域 | 分类/评分文件 | 职责 |
|---|---|---|
| 资讯洞察 | `domains/news/classifiers.py`、`domains/news/scorers.py` | AI 安全、Agent 安全、漏洞攻防、代码仓库分类；相关性、代码、影响力、新鲜度评分 |
| 能力洞察 | `domains/capabilities/scorers.py` | 代码仓库、论文线索、安全主题、可复现性评分 |
| 威胁洞察 | `domains/threats/repo_vuln_extractors.py`、`domains/threats/risk_scoring.py` | CVE、security issue、advisory、exploit/PoC、攻击面和继承 raw 分综合评分 |
| 漏洞洞察 | `domains/vulnerabilities/material_classifiers.py`、`domains/vulnerabilities/relevance_scorers.py`、`domains/vulnerabilities/evidence_extractors.py` | 判断 PoC/Exploit、深度技术分析、漏洞公告、影响范围；抽 CVE、版本、PoC、修复线索 |

### 35.3 设计原则

- 公共模块只负责统一结构和编排。
- 领域目录负责具体业务规则和信号解释。
- 评分必须输出 `breakdown`，避免只有一个不可解释总分。
- 证据抽取结果进入 `evidence_items` 和 `payload.extracted_evidence`。
- 真实模型可用于总结和复杂判断，但规则分类/评分必须能离线运行，便于回归测试和审计。

## 36. 威胁洞察：旧 repo-info/huawei 逻辑迁移说明

旧 `repo-info/huawei` 的核心不是单一 JSON 文件，而是一组确定性脚本 + OpenCode Agent 编排：

```text
huawei-code-scout
→ huawei-vuln-scout
→ huawei-vuln-filter
→ huawei-firmware-scraper
```

其中 Python 脚本主要负责 API 抓取、正则抽取、Markdown 表格解析、规则评分；OpenCode Agent 负责检查前置数据、编排脚本、webfetch 复核、解释结果、生成报告。

### 36.1 已迁移的确定性规则

旧 `vuln_filter_pipeline.py` 的五维评分已迁到：

```text
domains/threats/attack_surface_scoring.py
```

包含：

```text
language_vuln倾向
untrusted_input
historical_cve
complexity_stars
security_boundary
```

旧过滤/降权规则也已迁移，并写入 `scoring.signals.filtered`、`filtered_reason`、`deprioritized`。

### 36.2 已增强的 CVE/SA 证据解析

`domains/threats/repo_vuln_extractors.py` 解析：

```text
cves
sa_items
broad_sec_items
severity_counts
max_severity
source_types
scan_mode
has_security_repo_source
has_project_issue_source
has_exploit_signal
```

### 36.3 LLM 承接的旧 Agent 语义判断

新平台不让 LLM 执行 shell 或任意 webfetch，而是把旧 Agent 需要理解的判断转为结构化 LLM API 调用：

```text
pipelines/steps/threat_risk.py::ReasonThreatRiskStep
```

LLM 负责：

- 判断 broad security / issue 是真实安全问题还是普通 bug。
- 解释项目攻击面。
- 形成漏洞研究假设。
- 给出推荐跟踪级别和下一步动作。
- 对旧攻击面分、CVE/SA、security issue 进行综合语义复核。

确定性脚本负责事实抽取和评分；LLM 负责语义解释和复核。这是旧 OpenCode agent 模式在新平台中的生产化改造。

## 37. repo-info/huawei 完整迁移后的威胁 Pipeline

### 37.1 Connector 分层

```text
sources/connectors/threats/
├── gitcode.py
├── atomgit.py
├── hiascend.py
├── huawei_mirror.py
└── openx_huawei.py
```

connector 只负责获取 raw 数据。是否允许联网由 `live_source_fetch_enabled` 控制。

### 37.2 领域模块

```text
domains/threats/security_repo_discovery.py
domains/threats/security_file_parsers.py
domains/threats/issue_extractors.py
domains/threats/cve_scout.py
domains/threats/attack_surface_scoring.py
domains/threats/filters.py
domains/threats/validators.py
domains/threats/reports.py
```

这些模块把旧 `.opencode/scripts/` 的确定性逻辑迁移为平台领域代码。

### 37.3 Pipeline

```text
threats.huawei_full_migration_pipeline
```

流程：

```text
CVE 侦察
→ 攻击面评分/过滤
→ repo/CVE/firmware/mirror raw 导入
→ 威胁对象构建
→ 资产导入
→ LLM 语义复核
→ 报告 artifact
```

### 37.4 LLM 使用边界

不使用 LLM 的部分：采集、文件解析、CVE/SA 正则、Markdown table 解析、旧攻击面评分、过滤/降权。

使用 LLM 的部分：broad security 是否真实安全问题、普通 bug vs 安全问题、攻击面解释、漏洞研究假设、跟踪级别和下一步动作。

## 38. Huawei 输入模式

`threats.huawei_full_migration_pipeline` 不再拆分平行 live pipeline，而是通过参数选择输入模式：

```text
mode=local_raw
mode=live
```

### 38.1 local_raw

默认模式，读取：

```text
repo-info/huawei/data/huawei_repos.json
repo-info/huawei/data/huawei_repos_cves.json
repo-info/huawei/data/huawei_repos_scored.json
repo-info/huawei/data/firmware_aggregated.json
repo-info/huawei/data/ascendhub_aggregated.json
repo-info/huawei/data/huawei_opensource_mirrors.json
```

用于迁移回归、字段稳定性验证和离线开发。

### 38.2 live

通过：

```text
domains/threats/adapters/huawei_sources.py
sources/connectors/threats/*
```

重新抓取 GitCode / AtomGit / HiAscend / Huawei Mirror / OpenX Huawei 数据。该模式必须显式设置 `live_source_fetch_enabled=true`，否则 connector 返回 `live_source_fetch_disabled`。

### 38.3 单 pipeline 原则

不新增 `huawei_live_full_pipeline`，避免业务流程分叉。所有下游步骤消费统一的：

```text
context.outputs["huawei_source_records"]
```
