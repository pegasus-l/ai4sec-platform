# 资讯洞察实施参考

## 0. 文档目的与约束

本文档用于指导 AI4SEC 平台资讯洞察模块的前后端实现。目标是实现一个可以持续接收数据、筛选内容、辅助阅读、沉淀日报并向能力洞察流转的工作台，而不是静态展示页。

必须遵守仓库 `AGENTS.md`：

- 保持 `shadow-only`，不写生产库。
- 不修改旧系统生产脚本，不覆盖旧报告。
- 核心逻辑进入 `src/ai4sec_platform/`。
- 数据必须经过 raw artifact、标准化、去重、领域构建和质量审计。

## 1. 产品定位

资讯洞察回答：

> 最近有哪些 AI 安全、代码安全、Agent 安全相关内容值得阅读？

业务边界：

```text
资讯洞察：发现、筛选和阅读外部资讯
能力洞察：评估论文/项目是否值得复现、接入和转化
威胁洞察：发现值得挖掘的仓库、组件、固件和镜像
漏洞洞察：提取漏洞素材、根因模式和迁移知识
```

## 2. 第一版信息架构

只保留四个内容页签：

```text
资讯洞察
├── 今日精选
├── 全部动态
├── 日报
└── 专题时间线
```

不单独创建“论文”“项目”“阅读清单”页面。它们通过“全部动态”的筛选和状态实现：

```text
全部动态?item_type=paper
全部动态?item_type=project
全部动态?status=bookmarked
全部动态?status=read
全部动态?status=ignored
```

运营入口复用统一页面：

```text
采集任务 / 数据源 / 质量审计 / 人工队列
```

### 2.1 页面职责

| 页面 | 用户问题 | 第一版职责 |
|---|---|---|
| 今日精选 | 今天先看什么？ | 高价值条目、推荐理由、主题和来源概览 |
| 全部动态 | 所有内容在哪里？ | 搜索、筛选、排序、阅读和用户动作 |
| 日报 | 某天发生了什么？ | 按日期查看摘要、精选条目和主题分布 |
| 专题时间线 | 某个方向如何演化？ | 按主题聚合论文、项目和文章 |

### 2.2 用户主流程

```text
进入资讯洞察
  → 查看今日精选
  → 在全部动态中搜索/筛选
  → 打开详情
  → 已读、收藏、稍后阅读、忽略或反馈
  → 高价值论文/项目流转到能力洞察
  → 按日期回顾日报
  → 按主题查看时间线
```

## 3. 数据对象

### 3.1 NewsItem

建议使用 `domain_items` 作为持久化承载，但由 news service 输出稳定契约：

```json
{
  "id": 1,
  "domain": "news",
  "item_type": "paper",
  "title": "论文标题",
  "subtitle": "可选副标题",
  "summary": "面向用户的摘要",
  "highlight": "一句话重点",
  "source": "arxiv",
  "source_url": "https://arxiv.org/abs/2501.00001",
  "primary_date": "2026-01-01T00:00:00Z",
  "score": 88.5,
  "status": "new",
  "tags": ["agent-security"],
  "metrics": {"relevance": 90, "research_value": 85, "security_value": 88},
  "payload": {
    "external_id": "2501.00001",
    "authors": ["Author"],
    "topics": ["Agent Security"],
    "technical_points": ["技术点"],
    "code_url": "https://github.com/example/project",
    "paper_url": "https://arxiv.org/abs/2501.00001",
    "repo_full_name": "example/project",
    "stars": 100,
    "forks": 20,
    "language": "Python",
    "raw_artifact_id": 10
  }
}
```

第一版 `item_type`：

```text
paper / project / article / tool / report
```

### 3.2 状态和用户动作

采集/处理状态与用户阅读状态分开：

```text
处理状态：new / classified / selected / archived / needs_review
阅读状态：unread / read / bookmarked / later / ignored
```

无用户体系时先使用单一 `operator`，但结构预留 `user_id`。

### 3.3 日报和专题

```json
{
  "id": "news-report-2026-01-01",
  "report_date": "2026-01-01",
  "title": "AI4SEC 资讯日报",
  "summary": "日报摘要",
  "highlights": [1, 2, 3],
  "topic_sections": [{"topic": "Agent Security", "summary": "主题摘要", "item_ids": [1, 4]}],
  "status": "shadow"
}
```

专题第一版使用 `topics`、`tags` 和 `primary_date` 聚合，不引入复杂图数据库：

```json
{"topic": "Agent Security", "item_count": 12, "latest_at": "2026-01-01T00:00:00Z", "items": [1, 4, 7]}
```

## 4. 数据源和 Pipeline

### 4.1 第一批数据源

按顺序实现：

1. arXiv：论文标题、摘要、作者、发布时间、分类、论文链接。
2. GitHub：仓库名称、描述、star、fork、语言、更新时间、README 链接。
3. RSS：标题、摘要、发布时间、来源链接。
4. 本地 raw JSON：兼容现有 AI-for-Sec raw 文件，作为 fixture 和 shadow 输入。

后续接入 X、ASIS、Awesome List、GitCode 和内部数据源。

### 4.2 Pipeline 顺序

```text
CollectNewsSourcesStep
  → StoreNewsRawArtifactsStep
  → NormalizeNewsItemsStep
  → DeduplicateNewsItemsStep
  → ClassifyNewsItemsStep
  → ScoreNewsItemsStep
  → SummarizeNewsItemsStep
  → SelectNewsHighlightsStep
  → BuildNewsDomainItemsStep
  → BuildDailyReportStep
  → AuditNewsQualityStep
```

| Step | 输入 | 输出 |
|---|---|---|
| Collect | 数据源配置、时间范围 | `SourceFetchResult` |
| StoreRaw | connector 返回值 | raw artifact、manifest |
| Normalize | raw item | `NormalizedNewsItem` |
| Deduplicate | normalized items | 去重 item、合并关系 |
| Classify | 标题、摘要、来源字段 | 类型、主题、标签 |
| Score | 标准化条目 | 相关性、研究价值、安全价值、综合分 |
| Summarize | 标题、摘要、正文/元数据 | summary、highlight、technical_points |
| Select | 已评分条目 | 今日精选、日报候选 |
| Build | 处理结果 | domain items、evidence、queue |
| Report | 精选条目、主题聚合 | `DailyReport` artifact |
| Audit | 全流程产物 | 质量审计记录 |

### 4.3 运行模式

```text
shadow：允许联网采集，结果只写 shadow artifact 和 shadow 数据库
fixture：使用测试 fixture，不联网
legacy_raw：读取旧 raw JSON，不使用旧 processed 展示结果
```

## 6. 后端 API 契约

### 6.1 今日精选

```http

```

```json
{
  "domain": "news",
  "date": "2026-01-01",
  "kpis": {"new_count": 100, "highlight_count": 12, "paper_count": 30, "project_count": 25, "high_value_count": 15},
  "highlights": [],
  "topic_summary": [],
  "source_summary": []
}
```

### 6.2 全部动态

```http
GET /api/news/items
```

支持参数：

```text
query / item_type / source / topic / status
date_from / date_to / min_score
sort=score|published_at|updated_at
page / page_size
```

返回：

```json
{"domain": "news", "items": [], "page": 1, "page_size": 30, "total": 0, "filters": {}}
```

### 6.3 详情、日报、专题、来源

```http
GET /api/news/items/{item_id}
GET /api/news/reports
GET /api/news/reports/{report_date}
GET /api/news/topics
GET /api/news/topics/{topic}
GET /api/news/sources
```

详情必须包含基础字段、论文/项目专属字段、评分拆解、技术点、原始证据、关联条目、用户状态和下一步动作。

## 8. 可直接执行的阶段计划

### 阶段 A：契约和 fixture

新增 NewsItem、日报、专题、动作契约；准备 arXiv、GitHub、RSS、重复条目、缺字段和失败场景 fixture。

完成标准：前端可以脱离真实采集数据渲染四个页面。

### 阶段 B：标准化和去重

实现四类来源 normalizer、稳定 item key、多来源合并、论文与项目关联及单元测试。

完成标准：同一论文或项目不会重复展示。

### 阶段 C：处理和存储

实现分类、标签、评分、摘要、技术点、今日精选、evidence、日报构建。

完成标准：fixture 可以跑通 raw 到页面数据的完整链路。

### 阶段 D：API

实现今日精选、全部动态分页筛选、详情、日报、专题、用户动作、来源状态。

完成标准：API 不依赖前端拼装核心业务字段。

### 阶段 E：前端

实现导航、四个页面、详情抽屉、筛选、URL 状态、用户动作、空态和错误态。

完成标准：用户从进入页面到完成阅读和收藏不需要访问其他页面。

### 阶段 F：shadow 采集

实现 arXiv、GitHub、RSS shadow connector、运行记录、source artifact、失败隔离和质量审计。

完成标准：至少一个采集周期可以产出最新资讯，单个来源失败不阻断其他来源。

### 阶段 G：联调验收

完成 API smoke、pipeline 集成测试、前端构建、页面联调、运行手册和数据源配置说明。

## 10. 完成定义

第一版必须同时满足：

1. 用户可以打开资讯洞察并看到今日精选。
2. 用户可以在全部动态中搜索、筛选和排序。
3. 论文、项目、文章使用统一列表模型，并展示类型专属字段。
4. 用户可以完成已读、收藏、稍后阅读、忽略和反馈。
5. 日报和专题时间线基于同一批资讯条目生成。
6. arXiv、GitHub、RSS 至少有一套 shadow 采集链路可运行。
7. 所有结果可以追溯到 raw artifact 和处理运行。
8. 高价值论文/项目可以流转到能力洞察。
9. 采集、标准化、去重、评分、展示和用户动作都有测试覆盖。
10. 不绕过 `shadow-only`，不把旧 processed 展示结果当正式输入。
