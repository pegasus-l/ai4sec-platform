# 资讯洞察实施参考

## 0. 文档目的与约束

本文档用于指导 AI4SEC 平台资讯洞察模块的前后端实现。目标是实现一个可以持续接收数据、筛选内容、辅助阅读、沉淀日报并向能力洞察流转的工作台，而不是静态展示页。

必须遵守仓库 `AGENTS.md`：

- 保持 `shadow-only`，不写生产库。
- 不修改旧系统生产脚本，不覆盖旧报告。
- 核心逻辑进入 `src/ai4sec_platform/`。
- 数据必须经过 raw artifact、标准化、去重、领域构建和质量审计。

## 1. 产品定位

资讯洞察回答：

> 最近有哪些 AI 安全、代码安全、Agent 安全相关内容值得阅读？

业务边界：

```text
资讯洞察：发现、筛选和阅读外部资讯
能力洞察：评估论文/项目是否值得复现、接入和转化
威胁洞察：发现值得挖掘的仓库、组件、固件和镜像
漏洞洞察：提取漏洞素材、根因模式和迁移知识
```

### 1.1 技术地图约束

资讯洞察以 `configs/agent_tech_map.yaml` 为权威分类表。该配置由 `version3/agent_tech_map_clean.html` 提取，当前版本包含 7 个一级域、25 个二级域和 72 个叶子技术点。

每个正式收录条目至少匹配一个完整路径：

```text
一级域 dimension → 二级域 category → 叶子技术点 point
工具调用 → 工具集成总线 → MCP 协议
```

模型可以判断条目不相关，但不得创建地图之外的分类或技术点。规则分类仅作为模型不可用时的降级结果，并必须标记低置信度和待复核说明。

## 2. 第一版信息架构

只保留四个内容页签：

```text
资讯洞察
├── 今日精选
├── 全部动态
├── 日报
└── 专题时间线
```

不单独创建“论文”“项目”“阅读清单”页面。它们通过“全部动态”的筛选和状态实现：

```text
全部动态?item_type=paper
全部动态?item_type=project
全部动态?status=bookmarked
全部动态?status=read
全部动态?status=ignored
```

运营入口复用统一页面：

```text
采集任务 / 数据源 / 质量审计 / 人工队列
```

### 2.1 页面职责

| 页面 | 用户问题 | 第一版职责 |
|---|---|---|
| 今日精选 | 今天先看什么？ | 高价值条目、推荐理由、主题和来源概览 |
| 全部动态 | 所有内容在哪里？ | 搜索、筛选、排序、阅读和用户动作 |
| 日报 | 某天发生了什么？ | 按日期查看摘要、精选条目和主题分布 |
| 专题时间线 | 某个方向或事件如何演化？ | 自动聚合中文主题，并支持配置持续跟踪专题 |

### 2.2 用户主流程

```text
进入资讯洞察
  → 查看今日精选
  → 在全部动态中搜索/筛选
  → 打开详情
  → 已读、收藏、稍后阅读、忽略或反馈
  → 高价值论文/项目流转到能力洞察
  → 按日期回顾日报
  → 按主题查看时间线
```

### 3.2 状态和用户动作

采集/处理状态与用户阅读状态分开：

```text
处理状态：new / classified / selected / archived / needs_review
阅读状态：unread / read / bookmarked / later / ignored
```

无用户体系时先使用单一 `operator`，但结构预留 `user_id`。

### 3.3 日报和专题

```json
{
  "id": "news-report-2026-01-01",
  "report_date": "2026-01-01",
  "title": "AI4SEC 资讯日报",
  "summary": "日报摘要",
  "highlights": [1, 2, 3],
  "topic_sections": [{"topic": "Agent Security", "summary": "主题摘要", "item_ids": [1, 4]}],
  "status": "shadow"
}
```

专题分成两层。第一层是根据分类结果生成的“自动聚合主题”，使用中文 `display_topic` 和 `primary_date` 聚合，不引入复杂图数据库：

```json
{"topic": "Agent 安全", "item_count": 12, "latest_at": "2026-01-01T00:00:00Z", "items": [1, 4, 7]}
```

第二层是类似 ASIS 的“持续跟踪专题”，用于 Claude Mythos 漏洞挖掘这类具体事件。它不是普通标签，而是一个可配置、可暂停、可人工校正的持久对象：

```json
{
  "slug": "claude-mythos-security",
  "title": "Claude Mythos 漏洞挖掘",
  "one_liner": "持续跟踪 Claude Mythos 相关漏洞、利用研究和开源复现。",
  "aliases": ["Claude Mythos", "Mythos vulnerability"],
  "keywords": ["exploit", "jailbreak", "prompt injection", "RCE"],
  "sources": ["arxiv", "github"],
  "status": "active"
}
```

建议持久化 `news_topics` 和 `news_topic_memberships`。成员关系记录 `match_type`（规则、模型、人工）、`match_score`、`matched_terms`，允许运营人员移入或移出条目。采集完成后对启用专题增量匹配，专题详情按 `primary_date` 形成时间线。自动聚合主题继续用于发现方向，持续跟踪专题用于追踪具体事件，两者在页面上必须明确区分。

## 4. 数据源和 Pipeline

### 4.1 第一批数据源

六个来源分成直接内容源和发现源：

1. arXiv：论文直接来源。
2. GitHub：项目直接来源，按配置限额补充 README。
3. RSS：发现源，只提取 arXiv/GitHub 引用。
4. X：发现源，只提取帖子中的 arXiv/GitHub 引用。
5. ASIS：发现源，只提取已有情报中的论文/项目引用。
6. Awesome List：发现源，解析 Markdown 中的论文/项目链接。

所有来源首先保存完整 raw artifact。发现源的文章、帖子和列表条目不会作为正式资讯展示，最终只形成 `paper` 或 `project`。

### 4.2 Pipeline 顺序

```text
CollectNewsSourcesStep
  → ExtractNewsReferencesStep
  → NormalizeNewsStep
  → DeduplicateNewsStep
  → ResolveNewsLinksStep
  → GateNewsCandidatesStep
  → EnrichNewsCandidatesStep
  → BuildNewsItemsStep
  → BuildNewsDailyReportStep
  → AuditNewsStep
```

| Step | 输入 | 输出 |
|---|---|---|
| Collect | 数据源配置、时间范围 | `SourceFetchResult` |
| ExtractReferences | RSS/X/ASIS/Awesome 原始条目 | 论文/项目引用候选 |
| Normalize | raw item | `NormalizedNewsItem` |
| Deduplicate | normalized items | 去重 item、合并关系 |
| ResolveLinks | code URL、arXiv ID、repo 名称 | 双向论文—项目关联 |
| Gate | 候选基础信息、客观指标、技术地图 | 相关性、潜力分、初步地图路径、门控决策 |
| Enrich | 通过门控的候选、README、关联关系、初步路径 | 评分拆解、全部地图路径、中文摘要和展示文案 |
| Build | 已通过模型审阅的结果 | domain items、evidence、queue |
| Report | 精选条目、主题聚合 | `DailyReport` artifact |
| Audit | 全流程产物 | 质量审计记录 |

### 4.3 模型职责和缓存

生产运行通过 `LLMRouter` 使用 `.env` 中配置的 OpenAI-compatible 模型。模型调用拆为两次：第一次是低成本门控，只判断技术地图相关性、潜在价值和初步技术路径；只有 `pass` 或 `needs_review` 的候选才进入第二次深度评审。第二次负责论文/项目差异化评分、完整技术路径、中文主题、摘要、宣传一句话和亮点一句话。稳定 ID、URL 解析、确定性去重、显式论文—项目关联、加权总分和数据完整性检查继续使用确定性代码。

门控的 `map_relevance_score`、`potential_value_score` 以及深评的七项评分均严格使用 0–100 百分制。后端不再兼容或自动放大 0–1、0–10 分制；越界值按无效值处理。深评总分由后端按论文/项目权重计算，避免模型自行汇总造成尺度和权重漂移。

模型输出必须经过技术地图校验，非法路径会被丢弃；没有合法路径的候选不会进入前端。每次模型调用写入 `model_calls`，并以 `news_tech_map_gate` 或 `news_deep_review` 区分阶段，记录模型、输入、输出、延迟和错误。两个阶段分别缓存到 `gate_review` 和 `review`，缓存键由该阶段输入、技术地图版本和 prompt 版本共同计算；门控输入未变化时可跳过第一次调用，深评输入未变化时可独立复用第二次结果。

### 4.4 运行模式

```text
shadow：允许联网采集，结果只写 shadow artifact 和 shadow 数据库
fixture：使用测试 fixture，不联网
legacy_raw：读取旧 raw JSON，不使用旧 processed 展示结果
```

### 6.2 全部动态

```http
GET /api/news/items
```

支持参数：

```text
query / item_type / source / topic / status
date_from / date_to / min_score
tech_dimension / tech_category / tech_point（均可重复传入）
tech_match=any|all
sort=score|published_at|updated_at

```

技术筛选使用技术地图中的精确名称。前端以“热门技术点 + 三级技术地图抽屉 + 已选标签”呈现；维度、分类和技术点可以混合多选，默认命中任一条件，也可以切换为全部命中。`GET /api/news/tech-map` 为每个叶子技术点返回当前资讯数量，用于快捷筛选和树节点计数。

返回：

```json
{"domain": "news", "items": [], "page": 1, "page_size": 30, "total": 0, "filters": {}}
```

## 8. 可直接执行的阶段计划

### 阶段 A：契约和 fixture

新增 NewsItem、日报、专题、动作契约；准备 arXiv、GitHub、RSS 发现入口、重复条目、缺字段和失败场景 fixture。

完成标准：前端可以脱离真实采集数据渲染四个页面。

### 阶段 B：标准化和去重

实现四类来源 normalizer、稳定 item key、多来源合并、论文与项目关联及单元测试。

完成标准：同一论文或项目不会重复展示。

### 阶段 C：处理和存储

实现分类、标签、评分、摘要、技术点、今日精选、evidence、日报构建。

完成标准：fixture 可以跑通 raw 到页面数据的完整链路。

### 阶段 D：API

实现今日精选、全部动态分页筛选、详情、日报、专题、用户动作、来源状态。

完成标准：API 不依赖前端拼装核心业务字段。

### 阶段 E：前端

实现导航、四个页面、详情抽屉、筛选、URL 状态、用户动作、空态和错误态。

完成标准：用户从进入页面到完成阅读和收藏不需要访问其他页面。

### 阶段 F：shadow 采集

实现 arXiv、GitHub、RSS 发现入口 shadow connector、运行记录、source artifact、失败隔离和质量审计。

完成标准：至少一个采集周期可以产出最新资讯，单个来源失败不阻断其他来源。

### 阶段 G：联调验收

完成 API smoke、pipeline 集成测试、前端构建、页面联调、运行手册和数据源配置说明。

## 10. 完成定义

第一版必须同时满足：

1. 用户可以打开资讯洞察并看到今日精选。
2. 用户可以在全部动态中搜索、筛选和排序。
3. 论文和项目使用统一列表模型，并展示类型专属字段、中文主题和一句话导读。
4. 用户可以完成已读、收藏、稍后阅读、忽略和反馈。
5. 日报和专题时间线基于同一批资讯条目生成。
6. arXiv、GitHub 至少有一套 shadow 采集链路可运行，RSS 只发现论文或项目链接。
7. 所有结果可以追溯到 raw artifact 和处理运行。
8. 高价值论文/项目可以流转到能力洞察。
9. 采集、标准化、去重、评分、展示和用户动作都有测试覆盖。
10. 不绕过 `shadow-only`，不把旧 processed 展示结果当正式输入。
