## 1. 产品边界

### 1.1 当前页面目标

漏洞洞察页面不是“漏洞文章列表”，也不是“以洞找洞行动系统”。

当前阶段目标是：

```text
实时跟踪外部漏洞情报
  → 归一为素材证据
  → 按 CVE / 事件聚合
  → 抽取结构化漏洞知识
  → 人工字段级审核
  → 沉淀可追溯漏洞知识库
```

最终服务两个知识出口：

1. **安全大模型知识工程**：RAG、模型知识片段、结构化漏洞知识库；
2. **后续以洞找洞系统**：后续可消费已确认知识，但不在本页面实现迁移队列。

### 1.2 当前明确不做

以下属于后续行动系统，当前设计只预留接口，不在漏洞洞察主流程实现：

- 目标仓库绑定；
- 代码搜索命中；
- 复现任务；
- 漏洞迁移队列；
- 自动创建审计任务；
- 目标命中结果展示。

### 1.3 页面动线

V11 前端页面的推荐用户动线：

```text
今日情报
  1. 先看新 PoC / Exploit
  2. 再看新增 / 更新事件
  3. 审核模型抽取的知识字段
  4. 沉淀到漏洞知识库

情报素材库
  查看 URL 级证据、来源、素材类型、相关性、归并事件

漏洞事件库
  查看 CVE / 事件对象、证据链、知识完整度、待确认项

抽取审核
  字段级接受、修改、驳回、查看证据

漏洞知识库
  查看已确认 / 高置信知识，导出模型知识片段
```

## 3. 目标对象模型

### 3.1 对象层级

```text
RawArtifact
  原始 report / search result / crawled markdown / model response

VulnerabilityMaterial
  URL 级素材证据：文章、PoC、公告、补丁、讨论线索

VulnerabilityEvent
  漏洞事件：优先按 CVE 聚合；无 CVE 时按主题聚合

EvidenceSnippet
  支撑字段的证据片段：原文、代码、payload、patch、调用栈

VulnerabilityKnowledgeItem
  结构化漏洞知识条目：根因、触发条件、入口、关键函数等

KnowledgeFieldReview
  字段级审核记录：接受、修改、驳回、证据绑定
```

### 3.2 PoC 与事件的关系

```text
PoC / Exploit 是 Material 的一种
VulnerabilityEvent 是聚合对象
CVE 是最优连接键
```

规则：

1. 如果素材中存在 CVE，优先按 `cve_id` 归并事件；
2. 同一 CVE 下可以挂多个素材：公告、PoC、补丁、技术分析、复现文章；
3. 如果没有 CVE，但描述的是同一漏洞族或知识模式，建立 `kind=knowledge_topic` 的事件；
4. 无 CVE 事件必须标记为 `aggregation_confidence`，并进入抽样质量审计；
5. 前端必须展示 `cve_id / 无单一 CVE / 待 CVE 归一`，不能让用户误以为所有事件都有 CVE。

### 3.3 事件类型

| kind | 含义 | 示例 |
|---|---|---|
| `cve_event` | 有明确 CVE 的漏洞事件 | `CVE-2023-6241` |
| `multi_cve_event` | 一篇素材涉及多个 CVE，需要拆分或聚合 | Apache fuzzing 多漏洞文章 |
| `knowledge_topic` | 无单一 CVE，但可沉淀漏洞知识主题 | XXE、SQLi、HTTP Desync |
| `research_event` | 研究文章先作为研究事件，等待归一 | fuzzing 系列文章 |
| `advisory_event` | 官方公告先进入事件，等待 PoC/补丁/分析补充 | vendor advisory |

## 4. 数据 Schema 设计

### 4.1 `VulnerabilityMaterial`

建议在 `src/ai4sec_platform/domains/vulnerabilities/schemas.py` 中扩展：

```python
class VulnerabilityMaterial(BaseModel):
    material_id: str
    title: str
    url: str
    source_host: str
    source_type: str              # blog / github / advisory / nvd / vendor / exploit_db / manual
    material_type: str            # poc_exploit / tech_analysis / advisory / patch_commit / discussion / tutorial
    status: str                   # new / needs_review / linked_to_event / extracted / ignored
    summary: str
    cleaned_text_excerpt: str
    crawled_at: str
    published_at: str | None = None
    relevance_score: float
    extraction_confidence: float | None = None
    cve_ids: list[str] = []
    cwe_ids: list[str] = []
    affected_products: list[str] = []
    affected_versions: list[str] = []
    key_findings: list[str] = []
    search_keywords: str = ""
    event_id: str | None = None
    evidence_snippet_ids: list[str] = []
```

落库方式：

- `domain_items.domain = "vulnerabilities"`；
- `domain_items.item_type = "material"`；
- `domain_items.payload_json` 保存完整 schema；
- `evidence_items` 保存素材关键证据和模型判断依据；
- `metrics_json` 保存评分拆解、正文长度、来源质量等。

### 5.4 大模型使用设计

漏洞知识工程中，大模型只用于规则难以稳定覆盖的语义理解和结构化抽取，不负责直接确认事实、不直接发布知识、不绕过人工审核。

#### 5.4.1 使用大模型的环节

| 环节 | 是否使用大模型 | 目标 | 输出要求 |
|---|---|---|---|
| 正文清洗 / 关键段落识别 | 可选 | 从网页正文中识别漏洞分析正文、PoC、patch、影响版本段落 | `EvidenceSnippet` 草稿 |
| 素材相关性判断 | 可选 | 判断素材是否值得进入知识工程，区分浅层资讯、广告、教程、公告、PoC、深度分析 | `RelevanceJudgement` |
| 素材类型分类 | 可选 | 辅助区分 PoC/Exploit、技术分析、公告、补丁、讨论线索 | `MaterialClassification` |
| 无 CVE / 多 CVE 事件归并 | 可选 | 辅助判断素材是否属于同一事件、是否需要拆分 | `EventAggregationAdvice` |
| 证据片段抽取 | 是 | 抽取支撑知识字段的原文片段、代码片段、payload、patch、调用栈 | `EvidenceSnippet[]` |
| 结构化知识抽取 | 是 | 生成根因、触发条件、攻击入口、关键函数/API、利用原语、修复方式 | `VulnerabilityKnowledgeDraft` |
| 字段置信度判断 | 是 | 标记哪些字段需要人工复核 | `KnowledgeFieldReview.status=pending` |
| 知识片段生成 | 可选 | 将 confirmed knowledge 转为大模型 / RAG 片段 | `ModelKnowledgeSnippet` |
| 人工反馈后重分析 | 可选 | 用户驳回字段后重新抽取或重归并 | revised draft |

#### 5.4.2 不使用大模型或规则优先的环节

以下环节必须规则优先：

- CVE 正则抽取和大小写归一；
- URL / hash / 标题去重；
- 同 CVE 聚合；
- 来源健康、抓取状态、正文长度、空正文审计；
- 字段级接受 / 修改 / 驳回动作；
- confirmed 发布条件判断；
- pipeline run / task run / audit 统计。

规则能稳定完成的任务不调用模型，避免成本和幻觉。

#### 5.4.3 Agent 拆分

建议新增或改造以下任务型 Agent，放在 `src/ai4sec_platform/agents/`：

```text
agents/
├── vulnerability_relevance.py
├── vulnerability_event_reasoning.py
├── vulnerability_evidence.py
├── knowledge_extract.py
└── knowledge_snippet.py
```

| Agent | 输入 | 输出 | 说明 |
|---|---|---|---|
| `VulnerabilityRelevanceAgent` | `VulnerabilityMaterial` | `RelevanceJudgement` | 相关性、素材类型、保留/排除理由 |
| `EventDisambiguationAgent` | 一组疑似相关 material/event | `EventAggregationAdvice` | 只处理无 CVE / 多 CVE / 低置信归并 |
| `EvidenceSnippetAgent` | material 正文 + event context | `EvidenceSnippet[]` | 抽根因、触发、PoC、patch、影响版本证据 |
| `VulnerabilityKnowledgeAgent` | event + materials + snippets | `VulnerabilityKnowledgeDraft` | 结构化知识字段和字段置信度 |
| `KnowledgeSnippetAgent` | confirmed knowledge | `ModelKnowledgeSnippet` | 只基于已确认字段生成模型知识片段 |

所有 Agent 必须遵守：

- 输入是 Pydantic schema；
- 输出是 Pydantic schema；
- 通过 `LLMRouter` 调用模型；
- 记录 `model_calls`；
- 不读写任意文件；
- 不执行 shell；
- 不直接更新 DB，由 pipeline step 接收输出后写库。

#### 5.4.4 字段级模型输出要求

知识抽取中，每个字段必须包含：

```json
{
  "field_name": "trigger_condition",
  "value": "攻击者可控 XML 被默认启用外部实体的解析器处理",
  "confidence": 0.82,
  "evidence_snippet_ids": ["ev-001", "ev-004"],
  "reason": "原文明确给出 DOCTYPE 外部实体 payload 和 parser 默认行为",
  "review_status": "pending"
}
```

模型不能输出 `confirmed`，只能输出：

- `draft`；
- `needs_review`；
- `high_confidence_candidate`。

字段最终是否 confirmed，由规则校验和人工审核决定。

#### 5.4.5 防幻觉约束

模型提示词和校验器必须执行以下约束：

- 只能基于输入素材和 evidence snippets 回答；
- 没有证据的字段输出 `unknown` 或 `needs_review`；
- 禁止编造 CVE、CWE、版本、函数名、patch；
- CVE/CWE 以规则抽取为主，模型只能建议补充；
- 每个字段必须带 evidence refs；
- `evidence_refs` 为空的必填字段不能发布；
- 输出必须通过 schema validation；
- 所有模型调用记录 `model_call_id`。

### 5.5 AnySearch 接入策略

旧实现使用 AnySearch 作为关键词搜索入口。新平台仍然保留 AnySearch，但不把它写死在漏洞域业务逻辑中。

#### 5.5.1 是否继续使用

继续使用，原因：

- 旧漏洞素材采集已经验证 AnySearch 可作为外部漏洞素材发现入口；
- V11 的“今日情报 / 情报素材库”仍需要主动发现新文章、PoC、公告和技术分析；
- AnySearch 可以作为第一阶段 shadow 采集源，快速复用旧关键词体系。

但使用方式要调整：

```text
旧方式：漏洞域代码直接调用 anysearch client
新方式：SourceConnector 封装 AnySearch，Pipeline collect step 调用 connector
```

#### 5.5.2 推荐放置位置

优先放公共 connector：

```text
src/ai4sec_platform/sources/connectors/anysearch.py
```

如果第一阶段只服务漏洞域，也可以先放轻量 adapter：

```text
src/ai4sec_platform/domains/vulnerabilities/adapters/anysearch.py
```

但最终应收敛到公共 `sources/`，便于资讯、能力、漏洞多域复用。

#### 5.5.3 Connector 接口

```python
class AnySearchConnector(SourceConnector):
    source_name = "anysearch"

    def search(
        self,
        query: str,
        *,
        max_results: int = 20,
        domain: str | None = "security",
        zone: str | None = "cn",
        language: str | None = "zh-CN",
    ) -> list[RawSearchResult]:
        ...
```

返回的 `RawSearchResult` 至少包含：

- `title`；
- `url`；
- `snippet`；
- `score`；
- `source_name=anysearch`；
- `query`；
- `fetched_at`。

#### 5.5.4 Pipeline 接入点

AnySearch 进入：

```text
CollectExternalVulMaterialStep
  → AnySearchConnector.search
  → raw_artifacts
  → normalized_items
  → material pipeline
```

配置参数：

```yaml
vulnerabilities:
  sources:
    anysearch:
      enabled: true
      domain: security
      zone: cn
      language: zh-CN
      max_results_per_query: 20
      query_sets:
        - cve_recent
        - poc_exploit
        - vulnerability_research
        - vendor_advisory
```

#### 5.5.5 与旧关键词体系的关系

旧 `search_keyword.py` 中的关键词组可以迁移为配置化 query set：

| 旧关键词组 | 新 query_set |
|---|---|
| `KERNEL_KEYWORDS` | `kernel_vulnerability` |
| `PRIVILEGE_KEYWORDS` | `privilege_escalation` |
| `BUFFER_KEYWORDS` | `memory_corruption` |
| `RACE_CONDITION_KEYWORDS` | `race_condition_uaf` |
| `COMMAND_INJECTION_KEYWORDS` | `command_injection` |
| `LOGIC_KEYWORDS` | `auth_logic_bypass` |

第一阶段不需要全量迁移 1000+ 关键词，应先挑选每类 5-10 个高价值 query 做 shadow 验证。

#### 5.5.6 AnySearch 质量审计

AnySearch 结果必须进入质量审计：

- 搜索成功率；
- 空结果率；
- 重复 URL 率；
- 抓取成功率；
- 高相关素材比例；
- CVE 命中比例；
- PoC 命中比例；
- 低质量 / 广告 / 登录页比例。

质量结果写入：

```text
quality_audits.domain = vulnerabilities
quality_audits.audit_type = anysearch_source_quality
```

#### 5.5.7 替代和降级

AnySearch 是一个 source，不是平台唯一入口。后续可并行接入：

- NVD / CVE API；
- GitHub Search；
- vendor advisory RSS；
- Exploit-DB；
- manual import；
- 旧 `show/result/*.json`。

如果 AnySearch 不可用，pipeline 应允许：

- 跳过 AnySearch step；
- 继续处理旧 raw reports；
- 记录 source health 为 degraded；
- 不影响知识库读取。

## 8. 状态机设计

### 8.1 Material 状态

```text
new
  → classified
  → linked_to_event
  → extracted
  → archived

任意状态 → ignored
任意状态 → needs_review
```

### 8.2 Event 状态

```text
observing
  → needs_review
  → ready_for_extraction
  → extracted
  → closed

任意状态 → needs_merge
任意状态 → needs_split
```

### 8.3 Knowledge 状态

```text
draft
  → needs_review
  → confirmed
  → deprecated

draft / needs_review → reanalyze_required
```

### 8.4 Field Review 状态

```text
pending
  → accepted
  → modified
  → rejected
  → uncertain
```

知识入库条件：

- 必填字段均为 `accepted` 或 `modified`；
- 每个必填字段至少绑定一条 evidence；
- `completeness >= 0.75`；
- 没有 `rejected` 必填字段；
- CVE 事件必须有 `primary_cve_id`；无 CVE 主题必须有 `kind=knowledge_topic` 和聚合说明。

- 不调用旧生产脚本；
- 不写旧结果目录；
- 不把 AI 草稿直接作为 confirmed 知识；
- 所有 confirmed 知识必须可追溯到 evidence；
- 所有人工修改必须记录 reviewer 和理由；
- 所有模型调用必须记录 model profile、输入、输出和 run id；
- 外部 URL 打开只在前端作为链接，不在后端执行任意命令；
- 附件下载默认关闭或设大小限制。

## 16. 第一批文件级实施清单

建议按以下顺序实现：

1. `schemas.py`：补全 schema；
2. `entity_normalizers.py`：CVE/CWE/产品/版本抽取；
3. `evidence_extractors.py`：证据片段和字段 refs；
4. `event_aggregators.py`：CVE 优先聚合；
5. `builders.py`：创建 material/event/knowledge；
6. `pipelines/steps/vulnerability_event.py`：事件聚合 step；
7. `knowledge_extractors.py`：结构化字段抽取；
8. `field_reviews.py`：字段级审核；
9. `service.py`：V11 service；
10. `app/api/vulnerabilities.py`：V11 API；
11. `audits.py`：质量审计；
12. `tests/unit/*`：对应测试。

## 17. 与后续以洞找洞的接口边界

虽然本页面不做以洞找洞，但知识库应为后续系统提供可消费对象：

```text
Confirmed VulnerabilityKnowledgeItem
  → code_search_keywords
  → key_functions_or_apis
  → trigger_condition
  → vulnerable_pattern
  → evidence refs
```

后续以洞找洞系统只应消费 `status=confirmed` 的知识，不能直接消费 draft 或未审核字段。

## 18. 完成定义

本设计阶段完成的判定标准：

- 旧漏洞素材采集能力被完整纳入平台 shadow pipeline；
- V11 五个业务页面均有后端 API 数据源；
- 素材能按 CVE 优先聚合为事件；
- 无 CVE 素材能明确标记为知识主题；
- 知识抽取字段有证据引用；
- “待复核”字段有接受 / 修改 / 驳回入口；
- confirmed 知识能导出安全大模型知识片段；
- 运营页可看到采集、来源、规则、质量、人工队列；
- 全流程不写旧目录、不写生产库、不改生产脚本。
