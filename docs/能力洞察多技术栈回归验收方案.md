# 能力洞察多技术栈复现验收方案

## 1. 目标与边界

本方案用于完成生产化总计划第 917 项：在真实、公开、可追溯的项目上验证能力复现 Worker 的项目分类、任务生命周期、报告证据和能力卡回写。

这不是功能演示，也不是把任意 GitHub 仓库判为“能力已复现”。每个样本必须有固定提交、人工确认的合法用途和独立的验收记录。

执行范围：

- 仅克隆公开仓库的固定提交，不提交 PR、不发布包、不访问私有资源。
- 使用独立 SQLite 数据库、独立 `output/repro-regression/` Artifact 根目录和独立 Workspace，禁止使用生产数据库。
- 所有任务通过 `nested_docker` Profile 执行；`standard` Profile 在 rootless 出口强制执行器实现前保持禁用。
- 保持 Worker 的受控联网、任务级模型令牌、资源上限、日志脱敏和人工审批，不允许为追求通过率临时关闭安全控制。

## 2. 执行前置条件

开始任何真实任务前必须全部通过：

1. 部署 API/Model Gateway，并设置 `REPRO_LLM_BASE_URL=http://host.docker.internal:8000/api/model-gateway/v1` 或环境等价地址。
2. 宿主机管理员安装 `configs/repro-egress-helper/` 中的受限 helper。sudoers 只能允许指定 Worker 用户无参数调用 root-owned helper，不得直接授予 `iptables`、任意 shell 或全局防火墙管理权限。
3. `PYTHONPATH=src python -m ai4sec_platform.cli.repro_worker --check-config --profile nested_docker` 返回 `ok=true`。
4. 使用单独的 `AI4SEC_DATABASE_PATH`、`AI4SEC_OUTPUT_DIR` 和 `REPRO_WORKSPACE_ROOT`；执行前确认路径不包含生产数据库或生产 Artifact。
5. 每个样本固定 Git commit SHA，人工复查许可证、仓库活跃状态、启动命令、预期能力和允许的依赖域名。
6. 先在一个低风险 CLI 样本上运行完整任务，检查容器标签、出口计数、任务令牌撤销、报告和 cleanup 后，才允许批量执行。

固定 SHA 必须写入任务 `repo_commit`，由 Runner 执行 detached checkout 或同 SHA archive fallback；只在验收表中手工填写 SHA、任务实际仍克隆默认分支的结果无效。

## 3. 建议样本矩阵

以下是候选矩阵，不是已批准执行清单。执行时必须补全 `commit_sha`、确认核心命令和负责人，并把具体版本写入本文件的第 6 节。

| 波次 | 技术栈/模式 | 候选公开仓库 | 预期策略 | 验证重点 |
|---|---|---|---|---|
| 1 | Python CLI | `pallets/click` | cli | 依赖安装、命令执行、非 Web 成功证据 |
| 1 | Node.js CLI | `sindresorhus/ora` | cli | npm 安装、构建或测试输出 |
| 1 | Go CLI | `spf13/cobra` | cli | Go module、最小命令或测试 |
| 1 | Rust CLI | `clap-rs/clap` | cli | Cargo 构建、资源与超时行为 |
| 2 | Python Web | `tiangolo/fastapi` | local_web | 本地服务、真实路由闭环、端口代理 |
| 2 | Node.js Web | `expressjs/express` | local_web | Node 服务启动、核心路由验证 |
| 2 | Go Web | `gin-gonic/gin` | local_web | Go HTTP 服务、请求/响应证据 |
| 2 | Rust Web | `tokio-rs/axum` | local_web | Rust 服务启动和工作流证据 |
| 3 | Java CLI | `apache/commons-cli` | cli | Maven/Gradle 依赖、测试命令与报告 |
| 3 | Java Web | `spring-projects/spring-petclinic` | local_web | 较长启动、Web 超时与健康检查 |
| 3 | Docker Compose 项目 | 待人工指定 | nested_docker | Profile 审批、嵌套容器资源治理 |
| 3 | 真实 AI 安全能力项目 | 从资讯候选人工选定 | cli 或 local_web | 业务能力闭环、使用限制和人工质量审查 |

前两波至少完成 8 个样本；第三波补至 10–20 个。任何高资源、需要付费外部 API、包含攻击载荷或需要访问非公开目标的项目均不进入本轮默认清单。

## 4. 分波执行与停止条件

### 波次 1：CLI 基线

逐个执行 4 个 CLI 样本。每个任务必须产生真实命令、输出摘要、至少一个通过步骤和结果说明；缺任一证据不得标记 `success`。

停止条件：连续两个任务因环境/网络失败，或发现出口规则、任务令牌、容器标签、日志脱敏任一控制失效时停止批量执行并先修复平台。

### 波次 2：本地 Web

逐个执行 4 个 Web 样本，确认回环端口、代理 PID、核心工作流 `mode=real`、`verified=true` 和证据均写入结构化报告。仅首页 200、普通 CRUD 或服务启动都不构成成功。

停止条件：端口泄漏、容器未清理、停止请求无法终止运行态任务，或 Web 服务意外暴露到非回环地址。

### 波次 3：复杂项目与真实领域项目

Java、Compose 和真实 AI 安全项目必须在人工审批后单个运行。需要额外域名的任务走持久审批流程；不可复现、成本不可控或环境条件不满足的项目应报告为 `partial`/`failed`，不能通过修改状态伪造成功。

## 5. 单样本验收记录

每个样本记录下列字段，并以任务报告、Artifact checksum、Worker 日志和人工结论为证据：

```text
sample_id:
repository_url:
commit_sha:
license_reviewed_by:
strategy/profile:
approved_external_domains:
started_at / finished_at:
task_id / artifact_checksum:
expected_capability:
actual_status: success | partial | failed | timeout | stopped
actual_command_and_output:
core_workflow_evidence:
limitations_and_blockers:
container_cleanup_verified:
egress_counter_summary:
human_reviewer / review_decision:
```

验收通过不是“全部任务成功”，而是下列条件同时成立：

1. 任务、日志、SSE、报告、能力卡和 Artifact 的关联可追溯。
2. `success` 的报告满足当前 CLI/Web 证据门槛；失败与部分成功有可操作原因。
3. 任务令牌在结束后撤销，容器/代理/防火墙规则按状态清理，保留 Web 环境必须有明确人工验收理由。
4. 对每一技术栈统计成功率、平均耗时、失败阶段、重试次数、模型调用与人工修正率。
