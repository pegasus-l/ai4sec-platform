# 能力洞察施工方案

## 0. 文档定位

本文是 `ai4sec-platform` 中 **能力洞察** 模块的施工级文档。

它用于指导后续代码实现，覆盖：

```text
旧 v1/v2 大屏能力洞察代码如何迁移
新平台 domains/capabilities/ 各文件如何填充
数据对象和状态如何设计
Pipeline 如何拆分
API 如何提供（含 SSE 实时日志流）
评分维度如何与资讯侧共存
复现 runner 如何与 sysbox/docker 集成
测试如何闭环
```

本文遵循 `docs/平台总体架构设计.md` 的总体约束：

- shadow-only；
- 不写生产库；
- 不改旧生产脚本；
- 核心逻辑进入 `src/ai4sec_platform/`；
- 旧系统通过 `adapters/` 接入；
- `scripts/` 只保留薄 CLI；
- 前端通过平台 API 读取，不直接读旧 JSON。

## 1. 产品边界

### 1.1 当前阶段目标

能力洞察页面聚焦"从资讯到能力复现"的完整闭环：

```text
资讯洞察高分条目
  → 筛选有可复现代码的项目（GitHub repo / arxiv+code_url）
  → 派生为能力候选（capability_candidate）
  → 多维度能力评估（相关性/代码线索/可复现性/研究价值/安全价值）
  → 生成能力卡（capability）入库
  → 自动 / 手动触发复现任务（repro_task）
  → docker sysbox 容器 + opencode headless 复现
  → 流式日志实时推送（SSE）
  → 结构化报告（11+ 字段 JSON）回写能力卡
  → 能力转化（capability_conversion）：收藏 / 跟进 / 转化
```

最终服务两个出口：

1. **能力库**：沉淀可复现、可转化、已验证的能力资产
2. **复现队列与转化记录**：供运营跟踪 + 后续工作流消费

### 1.2 当前明确不做

以下属于后续扩展，当前只预留接口，不在能力洞察主流程实现：

- 跨用户协同（多人同时审核同一能力）
- 能力之间的依赖图（A 能力依赖 B 能力）
- 复现环境的容器镜像自动构建系统
- 能力库对外暴露为公共 API（供其他系统消费）
- 与外部 CI/CD 集成（自动跑测试套件验证复现结果）

### 1.3 页面动线

参考 `demo/data/ai4sec_tmg_sample/capability/` 的 4 份数据契约，前端推荐动线：

```text
今日能力
  1. 看今天值得复现的高分候选
  2. 触发复现或标记转化

能力库
  浏览所有已评估的能力卡 + 筛选（capability_type / sub_type / score / 状态）

复现验证
  1. 查看复现任务列表（repro_runs）
  2. 实时日志流（SSE）按操作类型上色（tool/read/exec/ok/warn/error/text）
  3. 查看结构化报告（11+ 字段）

能力转化
  跟进中的转化记录（持续观察 / 已转化 / 已放弃）
```

## 2. 关键决策汇总（9 决策）

经过对旧实现（`D:\漏洞挖掘\洞察工具\dashboard\test\old\` v1.0 与 `D:\漏洞挖掘\洞察工具\dashboard\test\new\` v2.0）的深入研究，并对照本平台设计文档与 demo 数据契约，确定以下 9 个关键决策：

| # | 决策点 | 最终方案 |
|---|---|---|
| 1 | ReproRunner 集成方式 | 复制旧 `repro.py` 829 行到 `domains/capabilities/adapters/repro_runner.py`，适配 `LLMRouter` + `core/env.py`，去掉硬编码 key（不沿用 v2 的 `sys.path.insert` 方案） |
| 2 | 运行环境 | WSL2（开发）+ 生产服务器（部署）都支持，所有环境差异通过 `.env` + `os.environ.get` 注入；代码不区分运行环境 |
| 3 | feedback_log 训练数据 | 复用新平台 `human_queue_items` 表；旧 `feedback_log` 的 action→queue_type、note→payload.note、ai_score/ai_hot→payload.ai_snapshot |
| 4 | 实时日志方案 | 采用 SSE（Server-Sent Events），用 FastAPI 原生 `EventSourceResponse` + React `useEventSource`；比旧 v1 的 WebSocket 更轻量；保留旧 `classify_log_line` 7 类上色逻辑 |
| 5 | sysbox + 端口代理 | 完整迁移 `_start_port_proxy`/`_stop_port_proxy`（socat + nsenter），因为 sysbox 内 `docker -p` 不可靠 |
| 6 | 能力评分 vs 资讯评分 | 两个分独立存在不同 `domain_items` 行；能力评估时把资讯 score 作为 5 维度之一的先验信号，不直接继承 |
| 7 | 复现报告 schema | 旧实现的 11+ 字段全部保留在 `capability_repro_tasks.report` 字段（JSON）；demo 7 字段只是前端展示层简化 |
| 8 | 复现 LLM key 来源 | 从 `.env` 的 `REPRO_LLM_API_KEY` 读取注入 REPRO_PROMPT，不硬编码 |
| 9 | 评估 LLM 模型选择 | 能力评估用 DeepSeek（除复现任务内 LLM 调用），通过 `LLMRouter` 路由 |

## 4. 数据契约

### 4.1 `capability_repro_tasks` 表（新增到 `core/db.py`）

```sql
CREATE TABLE IF NOT EXISTS capability_repro_tasks (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id         INTEGER NOT NULL,                  -- 关联 domain_items.id (capability)
    repo_url        TEXT NOT NULL,
    status          TEXT NOT NULL DEFAULT 'queued',    -- queued/running/success/partial/failed/stopped/timeout/cleaned
    container_name  TEXT NOT NULL DEFAULT '',
    workspace_path  TEXT NOT NULL DEFAULT '',
    log             TEXT NOT NULL DEFAULT '',          -- 累积日志（MVP 存库）
    result          TEXT NOT NULL DEFAULT '',          -- agent 最终总结（最后一段）
    created_at      TEXT NOT NULL,
    finished_at     TEXT NOT NULL DEFAULT '',
    cleaned_at      TEXT NOT NULL DEFAULT '',
    trigger         TEXT NOT NULL DEFAULT 'manual',   -- manual/auto
    report          TEXT NOT NULL DEFAULT '',           -- 结构化复现报告 JSON（11+ 字段，见 §4.3）
    web_port        INTEGER,                            -- Web 项目映射到主机的端口
    web_url         TEXT NOT NULL DEFAULT '',          -- Web 项目可访问 URL
    FOREIGN KEY (item_id) REFERENCES domain_items(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_cap_repro_item    ON capability_repro_tasks(item_id);
CREATE INDEX IF NOT EXISTS idx_cap_repro_status  ON capability_repro_tasks(status);
CREATE INDEX IF NOT EXISTS idx_cap_repro_created ON capability_repro_tasks(created_at DESC);
```

### 4.4 能力评估评分模型（多维度，1-5 + breakdown）

```python
# domains/capabilities/scorers.py（重写）

def score_capability_candidate(item: dict) -> ScoreResult:
    payload = item.get("payload") or {}
    news_item = payload.get("source_news_item") or {}
    news_score = (news_item.get("score") or 0) / 10.0   # 资讯分归一化 0-1

    code_url = news_item.get("code_url") or news_item.get("source_url", "")
    has_code = 1.0 if code_url else 0.0
    stars = news_item.get("stars", 0) or 0
    stars_factor = min(math.log10(stars + 1) / 4.0, 1.0)  # 10K stars → 1.0
    has_readme = 1.0 if news_item.get("highlight") else 0.0

    breakdown = {
        "relevance":       0.4 * news_score + 0.6 * has_relevance_signals(news_item),
        "code_clue":       has_code,
        "reproducibility": 0.5 * has_code + 0.3 * stars_factor + 0.2 * has_readme,
        "research_value":  0.7 * news_score + 0.3 * academic_signals(news_item),
        "security_value":  security_topic_signals(news_item),
    }
    final = sum(breakdown.values()) / len(breakdown)        # 0-1
    score = max(1, min(5, round(final * 5)))                 # 映射到 1-5
    return ScoreResult(score=score, breakdown=breakdown, ...)
```

**与资讯 score 的关系**：资讯 score 存在 `domain='news'` 的 `domain_items.score` 字段（1-10，单维度）；能力 score 存在 `domain='capabilities'` 的 `domain_items.score` 字段（1-5，多维度）。两者**不冲突、不覆盖**，能力评估时把资讯分作为先验信号注入 5 维度之一。

## 9. 风险与待确认项

### 9.1 已识别风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| WSL2 sysbox 安装 | 开发环境跑不起来 | 文档提供 WSL2 sysbox 安装步骤；开发阶段先做"提交任务 → 状态记录"的 mock，docker 部分单独验证 |
| DashScope 代理在内网访问 | 复现 LLM key 注入失败 | `.env` 配置 `DASHSCOPE_PROXY_URL`，`repro_runner.py` 优先读环境变量 |
| SSE 在 nginx 后被缓冲 | 实时日志延迟 | nginx 配置 `proxy_buffering off` + `proxy_read_timeout 3600s` + 不 gzip SSE endpoint |
| 旧 repro.py 829 行迁移遗漏 | 复现功能缺失 | 分 5 个 commit 迁移：① ReproRunner 类；② ReproManager；③ REPRO_PROMPT/WEB_REPRO_PROMPT；④ extract_report 三件套；⑤ sysbox + 端口代理 + classify_log_line |
| 能力评估 LLM 调用频率 | DeepSeek 配额耗尽 | 评估时先规则预筛，只对 has_code 的候选调 LLM；批量限流 |

- 能力转化记录是否需要邮件 / 钉钉通知
- 复现报告的归档策略（保留多久？清理规则？）
